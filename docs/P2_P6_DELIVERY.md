## 实际图编排

retrieve → route → requirements → plan 或 rule_plan → execute → feature → states → coverage → verify → goals → report → explain。

rule_plan绕过模型规划，但可选解释仍使用模型。确定性报告不依赖模型解释成功。需求覆盖与目标覆盖分别展示，日志增加goal_count、verified_goals、route及model_status。模型结构修复/HTTP恢复共享分析剩余调度预算，恢复不重置budget_started；同步I/O、基线汇总与最终文件写出不承诺严格端到端硬时限。

## 统计和溯源

条目生效率分母仍为全部业务有效条目，含flag未知。每个条件在实际未生效条目中的False数量分别除以未生效条目数及业务有效总体，两个分母都绑定群体产物；多条件可重叠。没有已知不满足条件但存在条件缺失时，原因目标标INSUFFICIENT；不把零计数说成已解释所有原因。

观测会话不跨会话拼接。用户已确认先按相邻可排序有效观测比较，不设自动归因窗口；未知与同时间冲突断开。质量排除及父群体之外的观测同样作为屏障，防止过滤后制造虚假相邻变化。状态段以segment_index标识，明细含全部观测而非仅头部预览。

追问继承父分析的不可变群体；变化事件只继承其前后记录。新的上下文保留parent_analysis_id、cohort_id及parent_event_id。修改范围、映射、ETL或特性文档版本时需要新分析。证据页面可按本轮record_id回查原始行；回查校验输入快照哈希。

## 性能验证

1. 30000条合成记录、210000条补充数值行：导入6.724秒，分析9.011秒，记录群体追问3.104秒；1000个观测会话、2000次预设变化；末端RSS304078848字节、产物3181802字节。
2. 294450条合成记录、约206万补充数值行：修复后分析71.093秒，群体追问23.497秒，追问98150条；9815个观测会话、19630次预设变化；末端RSS529891328字节，产物31039718字节。此次计时在移除不必要stream展开之前取得，保持原测量值，不声称优化后的速度。
3. 独立34000120行/440字段长表基准，512MB DuckDB限制、2线程：单字段0.094秒，窄范围10字段0.800秒，全范围10字段0.966秒，重复单字段0.101秒。数据生成后同进程读取，不代表冷缓存或完整导入。

29万条首次失败来自Windows深目录下DuckDB溢写路径过长，已为只读查询配置短且按数据集稳定分配的workspace_storage/query_tmp目录，维持512MB内存约束；不放宽SQL外部读取权限。追加按计划来源判断是否构造stream临时表，条目级计划不展开四流表。UI测试缓存隔离问题已修正。

这些RSS是末端进程值，不是峰值；阶段采样峰值另见performance.txt。模拟数据未覆盖现场4132列、1.85GB输入和3875万补充行的完整组合。新增scripts/benchmark_continuous.py支持--records与--extra-fields，所有运行产物在Git忽略目录。

## 用户验证步骤

1. 重启工作台，在原数据范围询问SPF生效比例；核对主回答分母、未知数与目标状态。
2. 询问SPF用户状态变化原因，在查询证据中查看SESSION_OBSERVATIONS、OBSERVED_CHANGES、SESSION_STATES完整产物。
3. 在左侧选择追问来源及实际未生效条目群体，追问条件；检查新结果只含该群体，输入范围必须保持一致。
4. 从OBSERVED_CHANGES复制完整event_id，在左侧填写后追问“这些变化的SPF条件”；只继承该事件前后记录。
5. 从证据中复制record_id，通过原始记录回查核验行位置与输入快照；不要把预览100行当成完整结果。
6. 需要用户级原因占比时，系统明确显示未启用，先确认分母和归类规则。
