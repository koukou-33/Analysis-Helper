| 待明确事项 | 实施期间的安全边界 | 最迟确认 |
| --- | --- | --- |

## 2. 分阶段实施

### P0：ServiceError 诊断与模型调用恢复（AH-010，优先）

涉及 services.py、performance.py、agent.py、配置示例、运行说明及模型适配测试。根因仍待确认；空 content 和 token 截断是待验证假设，不预设为已确认的 GLM 缺陷。

1. **P0.1 响应诊断与分类**：记录 plan/explain 用途、HTTP状态、请求ID、attempt、耗时、finish_reason、content类型/长度、可选推理内容长度与token usage。区分空输出、截断、JSON错误、响应结构错误、HTTP错误和超时；不记录密钥、完整prompt、业务原文或推理正文。
2. **P0.2 能力与预算配置**：按实际服务端点确认输出限制参数、推理控制和结构化输出能力；规划/解释分别设置有界预算。支持时降低推理强度或增加输出预算；不发送未经确认的厂商参数，不仅靠增加HTTP超时。
3. **P0.3 输入输出控制与有限恢复**：规划按问题筛选字段及依赖，解释采用完整业务汇总和必要证据；不以局部预览代表总体。空输出/截断仅在调整预算或规模后有限重试，建议最多一次；与HTTP重试共享累计时限，避免嵌套放大。不修补残缺JSON、不将reasoning_content当作最终答案、不静默切换模型。
4. **P0.4 独立embedding诊断**：核对embedding模型、接口及响应，保留BM25降级；不把chat输出问题作为embedding失败的根因。
5. **P0.5 调用状态及现场复验**：先区分模型成功/失败/未运行与外层流程返回；保留错误码和追踪ID。复验同一问题，比较实际响应元数据、重试次数及耗时。空需求误报业务完成在P1先修正，完整业务目标状态由P3实现。

验收：模拟覆盖null/空content、仅推理内容、明确长度截断、正常结束但畸形JSON、缺字段、合法对象及完整代码块、HTTP失败与超时；日志可区分原因且不含敏感正文；重试次数和时间受限；既有严格数值/引用验证不降级。现场必须取得有效最终JSON并通过QueryPlan/解释校验，或记录明确可定位的失败原因；只有后者时不得标记现场故障已解决。embedding独立验收。

交付拆分：P0.1和模拟测试可先完成；P0.2厂商配置与P0.5现场根因确认依赖实际端点信息/复验结果，未具备时明确待验证，不阻塞P1～P3的独立改造。P0负责调用稳定性，确定性业务报告由P1交付，prompt模板和全流程预算统一由P3承接。

### P1：业务汇总与确定性报告

涉及 evidence.py、agent.py、报告展示及 SPF 文档。

- 统一业务有效总体和实际1/0/未知统计；实现主生效率及分母标注。
- 将已有特性结果纳入确定性报告，报告实际状态、预期状态、条件缺失和预期/实际不一致。
- 增加计数守恒、AND 上界及完整规则与必要/阻断条件的兼容校验；冲突不得返回无依据的0。
- 模型不可用时仍输出通过核验的业务结论；模型调用诊断使用P0统一错误分类。
- 修正空需求列表自动判为整体完成的问题；分别展示模型调用状态与已有业务事实，完整目标完成度由P3接续。

验收：混合1/0/未知、全未知、零业务记录、多条件重叠、AND 计数矛盾、预期满足但实际关闭均有明确结果；固定样例的分子分母人工可复算。解释模型失败不影响已验证生效率发布。

### P2：统一分析上下文、群体与指标溯源

涉及 sessions.py、agent.py、plans.py、evidence.py；按职责新增上下文/溯源模块。

- 实现 AnalysisContext、CohortRef、MetricSpec 与派生产物父引用，绑定 Scope、数据/规则/质量版本、单位和去重键。
- 未生效群体物化或保存可验证关系引用，后续查询引用此群体，不重复独立生成条件。
- 保存原始行到结果的可回查链；跨轮证据必须显式导入并验证哈希、范围及版本兼容。
- 保留旧结果只读兼容；新结果采用独立结构版本，不静默改写旧报告。

验收：能从任一比例回查分子、分母和原始记录；拒绝跨数据集、错范围、错单位、错去重键、篡改文件与失效父引用；海量群体不写入 checkpoint。

### P3：业务目标驱动编排与 prompt 契约

涉及 agent.py、services.py、explanation.py、requirements 相关模块及新增 prompt 模板。

- 增加任务路由，已知结构化 SPF 走确定性核验主路径；保留通用描述与探索路径。
- 将特性执行、目标核账、业务一致性校验、报告生成从集中 execute/explain 中拆分，图中明确有限补查与终止条件。
- 需求从字段清单扩展为业务目标与依赖图，按目标记录 VERIFIED/INSUFFICIENT/FAILED/NOT_RUN。
- 模板独立版本管理，解释输入增加完整业务汇总和 MetricSpec；输出直接回答、事实引用、假设及未完成项，数值由程序渲染。
- 修复输入附必要失败输出和定位；保留严格结构与引用验证。统一记录查询、模型、修复、补查预算及恢复状态。

验收：SPF 已知规则无模型可完成；只问生效比例不扩大无关分析；原因查询依赖未生效群体；证据不足只阻断相关目标；预算耗尽/恢复不重复已完成工作；不自行启动同侪分析。

### P4：会话内状态段及变化解释

依赖 P2/P3；涉及会话查询、特性证据、状态事件产物与展示。

- 只在现有观测会话内排序和分段，不改变会话身份或跨边界生成转换。
- 状态段记录观测边界、数量及覆盖，转换事件引用前后记录、实际 flag、条件和同行门限。
- 对未知、质量排除间隔、时间歧义及多资源冲突保留明确状态；细节按本计划待确认项落实。
- 分离条目条件失败、会话涉及条件、转换事件解释；不自动设互斥首因或跨会话人数。

验收：连续生效、持续未生效、1→0→1、未知夹断、多个同时失败条件、门限自身变化、同时间冲突、跨会话同 CRNTI、无会话身份等样例可追溯。前后条件全满足而实际变化只输出不一致，不宣称根因。

### P5：连续追问与群体继承

依赖 P2～P4；涉及会话历史、规划输入和 UI。

- 保存 parent_analysis_id、目标群体、转换事件与分析口径；解析“这些用户/这些变化”引用。
- 多候选群体时澄清；范围、规则或数据版本改变时新建分析上下文。
- 实现原因对未生效群体和总体的比例（用户级口径确认后启用），所有比率绑定同单位的分母。
- UI 提供结论 → 指标 → 群体/转换 → 原始记录的溯源入口。

验收：完整重放“生效比例→未生效条件→涉及哪些会话→为何恢复生效”；同一会话多次转换不混同人数和事件数；原因重叠明确；上一轮模型文字被修改不能改变下一轮事实范围。

### P6：回归、规模验证及交付

- 运行边界与集成测试，完整回归；真实模型联调与无模型测试分别记录。
- 对接近6文件、29万输入行、3875万补充数值行的规模验证按需字段读取、会话排序、事件产物和连续追问。
- 记录环境、耗时、RSS、扫描/返回量、产物大小、超时及恢复；合成数据和真实数据验收分别标注，不承诺未测延迟。
- 同步详设、知识文档、问题台账、运行指南、版本迁移及交付状态。

验收：可从最终比例回查输入且重复运行一致；部分失败可恢复；旧结果可读；敏感原始数据与密钥不进入 prompt 日志或 Git。现场数据尚不可用时明确保留现场待验收状态。

## 6. 持续查询验证 Agent Loop（AH-012，已实施记录条件闭环）

用户已明确要求：每次提问后有数据和判据就持续验证，不把尚可核验的假设直接作为最终答案。以下保留L01～L05验收要求。L01～L04在记录谓词范围已实施；L05新增反例证明实际追加查询和回环，不以原82项回归替代闭环验收。通用时序/关联缺口检测和现场组合性能未纳入已完成范围。

### L01：目标、假设及验证任务契约

涉及新循环状态模块、agent.py、prompts.py、sessions.py。

- 实现LoopState、ValidationTask、HypothesisAssessment、MissingInformation及停止原因类型，绑定现有上下文、群体、规则与产物。
- 将已确认特性判据直接转为必要任务；新增假设必须给出可执行判据或明确缺少的规则，不能仅有文字。
- 以问题目标决定验证深度，纯统计问题不无限追查上游原因；用户级原因占比继续标待确认。

验收：字段存在/查询成功/引用有效不能单独使目标完成；任务与假设状态分离；范围、单位、规则和父群体错误被拒绝。

### L02：显式 LangGraph 查询—验证循环

涉及agent.py、plans.py、evidence.py、requirements.py及服务预算接口。

- 图中加入提出验证任务、输入盘点、计划、执行、判据评估、缺口更新、继续/停止判定的条件边。
- 现有数据可支持的必要验证自动执行，无需用户再问“继续”；残余未解释群体继续排队。
- 规范化指纹复用查询证据；共享累计查询/模型/修复预算，恢复不重置消耗。只允许当前范围与合法算子。

验收：一次提问至少覆盖“提出解释→追加查询→支持或反驳→更新结论”的真实循环；不得靠预先计算全部表格或用户二次点击冒充Agent Loop；重复等价查询不算进展。自动测试无需真实API。

### L03：缺口证明及完成审核

涉及字段目录、来源校验、业务一致性校验和最终发布门控。

- 检查相关字段目录、映射和目标群体中的有效性；记录缺失类型、证据、数量、时间/会话范围和影响。
- 严格区分DATA_INSUFFICIENT、CRITERIA_REQUIRED、TECHNICAL_FAILURE、UNSUPPORTED_OPERATION、BUDGET_EXHAUSTED、NO_PROGRESS及目标完成。
- 未查询但可查的项目不能说成数据缺失；有合法必要任务仍可执行时不能结束；零行按业务判据解释。

验收：Top-N遗漏、prompt字段裁剪、单次空结果、模型故障、预算耗尽均不会被错误报告为数据不存在。支持部分群体时，只对该群体作结论。

### L04：最终回答、界面和连续追问衔接

涉及reporting.py、explanation.py、prompts.py和app.py。

- 最终解释不得成为新假设的终点；新提出且必要、可验证的解释返回循环。暂时无法核验时须给出缺失数据/判据或技术原因。
- 回答显示直接结果、已验证解释、被反驳/未定解释及具体缺口；运行进度与阶段事实不得标为最终完成。
- 追问继承父群体/event_id后进入同一循环，不要求用户人工逐条发起验证；有歧义时只澄清受影响部分。

验收：“待验证假设”不能替代本可执行的查询；最终数值能回查完整产物；数据缺口清单能指导用户补数据，不猜字段名。保留手动探索入口与旧结果只读兼容。

### L05：反例驱动的端到端与规模验收

- 数据齐全：一个SPF问题内部持续查到必要目标闭合；验证查询被实际调用且进入证据链。
- 初始假设错误：后续查询反驳并修正解释，旧假设不能继续当结论。
- 部分满足：保留支持/不支持/未知子群体及重叠，不能用部分证据覆盖全部记录。
- 真正缺测：查明具体字段、群体和缺测数量，列出补充内容。
- 有数据缺规则：报告判据缺失；不编造门限、因果规则或时间窗。
- 技术失败/预算耗尽/重复查询：状态正确、无虚假“数据不足”、能够恢复且不重复成功工作。
- 最终生成器新增可验证解释：回环后再回答，不能绕过发布门控。
- 纯统计目标：验证比例后正常结束，不主动扩大到无限原因排查；用户级占比暂缓约束不被绕过。
- 按现有约29万条记录及3400万行长表基准测量循环额外扫描、内存、产物和耗时。合成与真实API/现场验收分别记录；无需重复ETL才可复用旧快照。

完成标准：L01～L04代码与上述反例通过后，才能宣布“单次提问内自动持续查询验证”已实现。实际数据/判据不足时能指出缺口；若仅因预算或技术问题结束，必须明确任务未完成。
