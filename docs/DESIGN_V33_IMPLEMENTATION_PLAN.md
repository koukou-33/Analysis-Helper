# SDS v3.3 修改实施计划

日期：2026-10-26。依据：[设计评审记录](DESIGN_V33_REVIEW.md)及用户已确认口径。

状态：2026-10-26 已按 P01～P08 交付本轮可运行增量，实际范围、验证及未覆盖边界见 [开发与验证记录](V33_DELIVERY.md)。以下保留原实施计划与目标，不将尚未确认的生产规则或现场验收标为完成。

## 1. 目标与实施原则

在现有 DuckDB、受控 QueryPlan、LangGraph 和 Streamlit 工作台上演进，先保证数据口径，再增加按问题核账、有限补查和解释能力。保留已有字段来源校验、不可变证据、查询预算、案例审核与历史恢复，不进行无关目录重构。

核心约束：

- 流控保留连续块原规则，完整块全留；日期、生产文件名和实际 instBfSinrGain 字段不回退。
- ueLayerNum 决定每条记录的有效流下标，selLayerNum 不替代。支持 1/2/4；8 流而只有四列时报告仅覆盖前四流。本期不承诺八列完整分析。
- 非法流数记录、可疑记录均整行退出全部业务统计，保留原始数据和质量统计。缺测与越界区分，不能把缺测自动判成可疑。
- 所有业务入口使用同一记录准入规则；指标缺测分母按准入后的实际有效流和有限值计算。
- 只分析当前问题相关内容；RSRP、NI、增益都不是每次必查。质量准入规则仍统一执行，不能因为问题没有问 RSRP 就让已判定可疑的记录重新参与 NI 统计。
- 责任层是排查方向，不是根因或免责结论。未填写字段归属和未经确认门限不能由模型补造。
- 同侪比较只由用户明确要求触发，按 logicCellId、分钟窗、相同 RB 区间、Slot、ueSymPos 匹配并排除目标 UE；必须说明空间差异未受控。

## 2. 分步骤交付

### P01：统一详设与可追踪任务

修改仓库详设 `5g_srs_diagnostic_agent_design_spec.md`，合并新版增量及评审修正，明确规则优先级、数据状态、统计口径和证据边界。修正连续块 SQL、窗口函数嵌套、汇总表字段引用和均值加权问题。

在 `docs/ISSUES.md` 建立本轮任务与缺陷条目，关联本计划 P01～P08、验收用例和完成提交；更新实施状态文档，区分历史交付与本轮待实现。已有模型输出问题关联原条目，避免重复记账。

验收：详设不再包含 instSubfGain、完整块删尾、可疑数值纳入业务均值、自动确认根因等冲突口径；每个评审变更有对应实施步骤。外部原始设计文件保留作为评审输入。

### P02：规范字段映射与元数据

涉及 `schema.py`、`knowledge.py`、输入契约及字段资料。

1. 定义版本化字段模型：原始名称/列位置、标准名称、别名、单位、数组域、责任层、字段角色、有效索引约束、出处和版本。
2. 导入用户 Markdown 表：兼容范围 `[0-3]` / `[0~255]`，展开时保留原条目；空白不覆盖非空说明；重复项语义冲突生成报告，不任意择一。
3. 将 ueLayerNum、ueSymPos 等必要字段接入契约；增益归 L1测量，userNum 保留“任务内码分用户个数”含义。责任层与流/波束分类分开。
4. 大字段表按字段/字段族建索引，不依赖整篇前部摘要。未归属字段标为待确认；isRsrp 索引约束绑定 rxAntNum，缺少约束依据时显式报告未知。

建议维护方案：用户 Markdown 作为人工字段语义输入，经校验生成带源哈希的结构化运行目录；现有 JSON 保留 CSV 解析、别名及类型契约，禁止重复独立维护同一归属。此方案在 P01 详设中明确后实施。

验收：已填写归属可逐项追溯；重复、空白、范围及未知字段测试通过；ueSymPos 不被近义列自动替换；未确认的范围不进入生产异常判定。

### P03：实际流数、整行准入与数据版本

涉及 `pipeline.py`、`database.py`、`queries.py`、`plans.py`、`sql_executor.py`、`domain_policy.py`、`synthetic.py`。

1. 保存原始流数、解析值、流数状态、可观察流范围及异常原因。1/2/4 按记录生成有效流掩码；8 保留实际配置，标记部分覆盖。
2. 将质量原因拆开保存，并生成统一业务准入标志。任何已确认可疑条件成立，或流数非法，整行退出业务分析；多重原因允许并存。
3. 所有基础汇总、资源/流/小区时频表、scoped 查询、特性与手动 SQL 业务入口落实同一准入条件。质量审计使用单独用途入口，不能混入业务均值。
4. 有效配置内全空/零值不自动删流；流均值使用各流有效样本，流间差值使用同记录成对有效样本，并披露分母。
5. 提升 ETL/统计策略版本及数据身份，原始快照可重新生成新数据集；旧数据、证据与会话保留并标明旧口径，不静默混算。

验收：人工小样本覆盖 1→2→4、8 流四列、空/0/负数/小数/不支持流数、单项越界导致整行排除、正常零值及单项缺测。基础统计、计划查询和手动查询在同范围得出相同结果。连续块与会话规则回归通过。

### P04：按问题建立需求与覆盖账本

涉及 `knowledge.py`、`plans.py`、`evidence.py`；新增需求及覆盖模块。

1. 每项需求保存来源/版本、与问题的关系、指标、维度、范围、核查目的和必需程度，覆盖当前完整 Scope；Top-10 只限制画布展示。
2. 分开记录字段存在性、有效性、执行状态：不存在、全空、解析失败、当前范围无有效值、未查询、成功、失败、不支持等不能混为一个状态。
3. 覆盖必须绑定成功产物、字段来源及核查目的；SQL 中出现字段、仅用于过滤、零行结果均不能自动等同于有效验证。零行可以是已执行但证据不足。
4. 将全局“增益全空则停止解释”改为按问题判定。没有准入业务记录时只返回质量事实；无关指标缺测不阻断相关问题。

验收：只问 NI 且增益全空时仍可分析有效 NI；只问增益不会强制查询 RSRP；失败查询不能算已覆盖；派生字段能沿步骤追溯来源；未支持数组明确列出。

### P05：LangGraph 有限补查与案例路径

涉及 `agent.py`、`plans.py`、`sessions.py`、`cases.py`。

目标流程：检索 → 整理相关需求 → 计划及来源校验 → 执行 → 覆盖核账 → 必要补查 → 证据验证 → 解释。

1. 复用受控算子，不开放自由 SQL 或全表权限。
2. 补查只处理未完成的相关需求；配置总时间、轮数、字段批量和产物上限，沿用单次查询预算。结构修复重试与业务补查分别计数并受总预算约束。
3. 无新增覆盖、预算耗尽、不支持或重复失败时终止，保留成功事实和未覆盖原因，不把部分完成标成全部成功。
4. 案例命中只进入判据验证，证据不足或不符转探索并记录原因；保留 FeatureSpec、审核和回放能力。
5. 检查点保存需求、预算消耗和产物引用；恢复不得重置预算、重复已完成查询或覆盖旧证据。

验收：部分补查成功、无进展、超时、重复失败、中断恢复均能有限终止；相似案例不能直接形成根因结论。

### P06：跨层统计与显式同侪比较

涉及 `queries.py`、`plans.py`、`charts.py` 及需求模型。

增加问题需要的 userNum、RB 区间变化、实际流数与趋势统计，逐项写明公式、单位、窗口及样本量。语义或门限未定的指标先报告描述性事实，不输出故障判定。

同侪请求在请求层保存显式开关及来源，模型计划不能自行授权。缺少匹配维度时返回无法完成比较，不放宽到其他 RB、Slot 或符号。候选样本也应用业务准入规则；基线说明聚合方法和每个 UE 样本量，避免不透明地让高频采样 UE 主导结果。

验收：默认请求不产生跨 UE 查询；显式请求严格排除目标 UE，按所有已确认维度匹配；无同侪、匹配字段缺失及样本不足有明确状态；空间差异提示进入证据与最终解释。

### P07：模型输出兼容与解释约束

涉及 `services.py`、`explanation.py`、`domain_policy.py`、`evidence.py`。

1. 接受原始 JSON 对象及仅被完整单个 Markdown JSON 代码块包裹的对象；去外壳后仍执行严格 JSON 和结构校验，不从混杂正文中任意截取对象，不自动修补错误数值。
2. 对引用字段中明确的 `artifact:` / `artifact：` 外壳做有限规范化，再验证完整 ID 属于本轮证据；未知、截短、跨轮 ID 继续拒绝。保存规范化审计信息，数值/单位校验不降级。
3. 展示表号映射到不可变 artifact_id；责任层展示已支持、待核查和缺少证据，不能从“未观察”推导无责。
4. 四流倒序只作为待核查现象，缺测不推断采集故障。必要判据满足不代表充分证明根因；解释失败时明确拒绝原因并保留通过验证的事实。

验收：JSON 代码块、两种冒号、未知引用、错误数值、混杂正文等正反用例通过；按问题粒度缺测策略与 P04 一致。

模型输出兼容修复可在 P01 后单独提前交付；完整解释与责任层展示依赖 P02～P05。

### P08：工作台、规模验证与交付

涉及 `app.py`、`performance.py`、`scripts/benchmark_scope.py`、测试、运行说明及状态文档。

- 展示业务准入/排除数量、原因、实际流数、四列覆盖边界、需求状态、补查进度和失败详情；历史结果明确规则版本。
- 延续补充字段按需读取，禁止先将 440 个字段全量 pivot。性能日志增加字段批量、扫描/返回规模、补查轮数、累计预算等安全元数据，不写密钥或原始敏感内容。
- 用 440 个补充数值字段、约 3400 万行长表复验：少量字段、分批多字段、窄/宽 Scope、重复查询及恢复。记录硬件、数据规模、耗时、进程 RSS、超时和成功状态，与相同环境旧基线比较。
- 单次查询应遵守配置时限和内存预算；超限须可诊断降级。未实测前不承诺固定延迟，也不以小样本替代大规模通过。
- 运行相关回归、完整测试和 UI 操作链；真实模型联调与模拟测试分别记录，真实规模验收与合成数据结果分别记录。

验收：正常分析、全异常、部分覆盖、模型格式错误、无匹配同侪、恢复旧会话均有可理解的结果；确认现场性能后再标记本轮验收完成。

## 3. 依赖和里程碑

主顺序：P01 → P02 → P03 → P04 → P05 → P06 → P07 → P08。P07 的输出格式兼容部分可以提前。

| 里程碑 | 完成步骤 | 用户可验证的结果 |
| --- | --- | --- |
| M1 口径正确 | P01～P03 | 实际流数生效，可疑/异常记录整行排除，新旧结果可区分 |
| M2 按问题分析 | P04～P05 | 问题需求可见，有限补查，无关缺测不阻断分析 |
| M3 解释与对比 | P06～P07 | 显式同侪比较，输出格式兼容，责任方向有证据约束 |
| M4 可交付验证 | P08 | UI 完整，回归及规模验证有记录，使用与迁移说明齐全 |

每一步完成后通知用户：具体变化、验证结果、剩余限制和下一步。每一步形成独立可审阅变更，提交与推送时不包含 .env、真实数据、运行存储或临时产物。

## 4. 剩余细节与建议默认值

以下是实施建议，不表示用户已确认的新业务规则；仅阻塞依赖它的功能，不阻塞已确定的基础改造。

| 事项 | 建议处理 | 最迟确定阶段 |
| --- | --- | --- |
| 字段映射权威源 | Markdown 维护语义，校验生成结构化目录；JSON 维护解析契约，不双写归属 | P01/P02 |
| uwTime 说明疑似日期笔误 | 保持当前时间解析契约，单独核对说明；不改成日期 | P02 |
| 空白归属、重复字段、生产门限 | 空白保持未知，冲突列出；未确认规则不启用 | P02/P03 |
| 一分钟窗口 | 建议按解析后的事件时间自然分钟分桶，明确时间基准；非滑动窗 | P06 |
| 多符号记录 | 无法确认符号覆盖时，不纳入只按起始符号匹配的基线，并显示原因 | P06 |
| 趋势及同侪基线公式 | 明确采样、分母、聚合方式后实现；不默认将样本差异判为异常 | P06 |
| 补查默认预算 | 沿用现有单查询限制，先配置少量轮数，再由 P08 基准调整；必须有总预算 | P05/P08 |

## 5. 发布与回退

新规则以新数据集和策略版本启用，建议先对同一快照并列验证。若出现回归，回退代码并打开与旧版本匹配的旧数据集和会话；不得用旧代码读取新结构后继续写入，也不修改历史证据。新规则结果必须重算，不能只更新历史报告标题。

实施完成时同步详设、字段契约、知识约束、测试、问题台账、运行说明和交付状态；尚未完成的现场验收保持待验证标识。
